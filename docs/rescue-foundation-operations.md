# A0 rescue foundation rollout

The additive `20261019_rescue_foundation` migration creates `RescueRequest` and append-only `RescueRequestEvent` tables. It does not rewrite or convert flood reports. Apply only after a database backup and reviewed `npx prisma migrate status`, then deploy the matching API version. Existing application versions continue to use flood reports during a rolling rollout; the new API must not receive traffic before the migration. Rollback the application to the previous version if needed. Leave the new tables intact on rollback to preserve already-received emergencies; do not drop or truncate them. Reconcile them with operators before any later contraction.

Public intake requires a verified user session and a fresh `Idempotency-Key`. Admin-assisted intake requires an administrator, explicit `intakeChannel: "admin_assisted"`, and resident contact. Linking a flood report through admin intake requires `linkConsentConfirmed: true` after reviewing consent and the report. Historical “Rescue Needed” reports are never imported automatically. The receipt means *received by Flood Watch*, not dispatched. A case owner is an administrator coordinator, not a responding team. `en_route` requires a manually recorded confirmed team reference; this software does not notify a responder or verify dispatch independently.

Precise location, contact and vulnerability details are sensitive. Public detail is owner-only; admin detail is role-protected; general maps and analytics must not consume these DTOs. Internal event notes are omitted from public responses and error logs must not include request payloads. The database and backups require access control and encryption at rest by the operator. No automatic retention or deletion job is introduced: operators must approve a retention period, backup lifecycle and deletion/legal-hold procedure before production rescue intake is enabled. User deletion is deliberately restricted by event actor foreign keys; do not cascade-delete rescue history.

For an isolated integration check, set `TEST_DATABASE_URL` to a disposable PostgreSQL database, apply migrations there, and run `npx tsx --test tests/integration/rescue.integration.test.ts`. Never point that setting at production. Confirm owner/admin reads, replayed IDs, one intake event, 409 stale actions, and public timeline updates before enabling the UI. U5 and A4 remain separate work: the existing public and admin rescue screens still show their old preview behavior until connected to these APIs.
